# EasySwap NFT 市场 — 需求规格说明书

## 1. 文档信息

| 项目 | 内容 |
|------|------|
| 项目名称 | EasySwap NFT 去中心化交易市场 |
| 文档版本 | v1.0 |
| 编写依据 | `contracts/` 目录下 Solidity 智能合约源码 |
| 技术栈 | Solidity ^0.8.19、OpenZeppelin Upgradeable、Hardhat |

---

## 2. 项目概述

### 2.1 项目背景

EasySwap 是一个基于以太坊的 NFT 去中心化交易协议。用户可以在链上创建、取消、修改订单，并通过订单撮合完成 NFT 与 ETH 的交换。协议采用订单簿（Order Book）模型，支持卖单（List）与买单（Bid）两种方向，并通过独立的 Vault 合约托管交易资产。

### 2.2 项目目标

- 提供链上 NFT 固定价格交易能力
- 支持单品挂单与集合出价两种交易模式
- 提供订单簿查询能力，便于前端展示最优价格与订单列表
- 支持协议手续费抽取，为平台运营提供收入来源
- 支持合约可升级部署，便于后续功能迭代

## 3. 用户角色

| 角色 | 描述 | 主要权限 |
|------|------|----------|
| 普通用户（Maker/Taker） | NFT 持有者或买家 | 创建订单、取消订单、修改订单、撮合成交 |
| 协议 Owner | 合约部署者/管理员 | 设置协议费率、设置 Vault 地址、暂停/恢复合约、提取合约内 ETH |
| OrderBook 合约 | 系统内部角色 | 唯一可调用 Vault 资产操作的地址 |

## 4. 功能需求

### 4.1 订单管理

#### FR-001 创建订单（makeOrders）

系统应支持用户批量创建订单，具体要求如下：

- **卖单（List）**
  - 用户将指定 ERC721 NFT 托管至 Vault
  - 每个卖单的 NFT 数量必须为 1
  - 卖单类型必须为 `FixedPriceForItem`（单品固定价）
  - 订单创建成功后写入订单簿，并发出 `LogMake` 事件

- **买单（Bid）**
  - 用户将 ETH 托管至 Vault，金额为 `price × amount`
  - 买单的 NFT 数量必须大于 0
  - 支持两种买单类型：
    - `FixedPriceForCollection`：对整个 NFT 集合出价
    - `FixedPriceForItem`：对指定 tokenId 出价
  - 创建买单时，调用者需通过 `msg.value` 支付所需 ETH

- **通用约束**
  - 调用者必须是订单 maker
  - 订单价格不能为 0
  - salt 不能为 0
  - 订单未过期（expiry 为 0 表示永不过期，或 expiry > 当前区块时间）
  - 同一订单哈希不能重复创建（filledAmount 为 0）
  - 不满足条件的订单应跳过并发出 `LogSkipOrder` 事件，不中断批量操作
  - 若 `msg.value` 超出实际需要，多余 ETH 应退还给调用者

#### FR-002 取消订单（cancelOrders）

系统应支持用户批量取消未完全成交的订单：

- 仅订单 maker 本人可取消
- 仅当 `filledAmount < nft.amount` 时可取消
- 取消卖单：Vault 将 NFT 退还给 maker
- 取消买单：Vault 将剩余 ETH（`price × 剩余数量`）退还给 maker
- 订单从订单簿移除，filledAmount 标记为已取消（CANCELLED）
- 返回每笔取消操作的成功/失败状态数组
- 取消成功发出 `LogCancel` 事件

#### FR-003 修改订单（editOrders）

系统应支持用户修改已有订单的价格、数量、过期时间、salt 等参数：

- 不允许修改：saleKind、side、maker、collection、tokenId
- 不允许修改已完全成交或已取消的订单
- 修改流程：移除旧订单 → 取消旧订单状态 → 创建新订单 → 迁移 Vault 资产
- 卖单修改：Vault 中 NFT 绑定关系从旧 orderKey 迁移到新 orderKey
- 买单修改：根据新旧剩余 ETH 差额，多退少补
- 返回新 orderKey 数组；失败时返回 `ORDERKEY_SENTINEL`

### 4.2 订单撮合

#### FR-004 单笔撮合（matchOrder）

系统应支持买卖双方订单的链上撮合：

- 卖单 side 必须为 `List`，买单 side 必须为 `Bid`
- 卖单 saleKind 必须为 `FixedPriceForItem`
- 买卖双方不能为同一人
- 资产匹配规则：
  - 买单为集合出价（FixedPriceForCollection）：不要求 tokenId 一致
  - 买单为单品出价（FixedPriceForItem）：collection 与 tokenId 必须一致
- 双方订单均未完全成交

**卖方发起撮合（sellOrder.maker == msg.sender）：**
- 卖方不能附带 ETH（msg.value == 0）
- 以买方出价（buyOrder.price）作为成交价 fillPrice
- 从 Vault 提取买方 ETH，扣除协议费后转给卖方
- NFT 从 Vault 转给买方（链上订单）或直接从 maker 转给买方（链下签名订单）

**买方发起撮合（buyOrder.maker == msg.sender）：**
- 链下买单：需附带 msg.value >= fillPrice
- 链上买单：从 Vault 提取 ETH，成交价以卖单价格为准
- 若买方出价高于成交价，退还差额
- NFT 从 Vault 转给买方

#### FR-005 批量撮合（matchOrders）

系统应支持批量撮合多组买卖订单：

- 通过 delegatecall 调用内部 `matchOrderWithoutPayback` 实现单笔隔离
- 单笔失败不中断整批，失败信息通过 `BatchMatchInnerError` 事件记录
- 统一计算并退还买方多余的 ETH

### 4.3 订单查询

#### FR-006 获取最优订单（getBestOrder）

- 按 collection、tokenId、side、saleKind 查询当前最优有效订单
- 自动跳过过期订单
- 按 saleKind 过滤不匹配的买单类型

#### FR-007 分页获取订单列表（getOrders）

- 支持按价格档位分页遍历订单
- 支持从指定 orderKey 继续查询（游标分页）
- 自动跳过过期订单及 saleKind 不匹配的订单
- 返回订单数组及下一页起始 orderKey

### 4.4 资产管理（Vault）

#### FR-008 ETH 托管

- OrderBook 可将 ETH 存入/取出/编辑（按 orderKey 索引）
- 每个 orderKey 独立记录 ETH 余额

#### FR-009 NFT 托管

- OrderBook 可将 ERC721 存入/取出/编辑（按 orderKey 索引）
- 支持直接从 maker 到 taker 的 ERC721 转移（链下卖单场景）
- 支持用户批量转移 NFT（batchTransferERC721）

#### FR-010 访问控制

- 仅已配置的 orderBook 地址可调用 Vault 的资产操作函数
- Owner 可更新 orderBook 地址

### 4.5 协议管理

#### FR-011 协议费率

- 初始化时设置 protocolShare（基点制，TOTAL_SHARE = 10000）
- 最大费率不超过 MAX_PROTOCOL_SHARE（1000，即 10%）
- Owner 可通过 setProtocolShare 动态调整
- 撮合成交时，从 fillPrice 中扣除 `fillPrice × protocolShare / 10000` 作为协议费

#### FR-012 合约管理

- Owner 可设置/更新 Vault 地址（setVault）
- Owner 可暂停/恢复合约（pause / unpause），暂停期间禁止交易操作
- Owner 可从 OrderBook 合约提取累积 ETH（withdrawETH）
- 合约支持 UUPS/Transparent Proxy 可升级部署

## 5. 数据需求

### 5.1 订单数据结构

| 字段 | 类型 | 说明 |
|------|------|------|
| side | enum | List(0) 卖单 / Bid(1) 买单 |
| saleKind | enum | FixedPriceForCollection(0) / FixedPriceForItem(1) |
| maker | address | 订单创建者 |
| nft.tokenId | uint256 | NFT Token ID |
| nft.collection | address | ERC721 合约地址 |
| nft.amount | uint96 | 数量（卖单固定为 1，买单可 > 1） |
| price | uint128 | 单价（ETH，wei） |
| expiry | uint64 | 过期时间戳（0 表示永不过期） |
| salt | uint64 | 随机盐值，保证订单唯一性 |

### 5.2 订单唯一标识

- 订单 Key（OrderKey）= keccak256(EIP-712 风格 ORDER_TYPEHASH + 订单各字段)
- 用于索引订单、Vault 资产及成交状态

## 6. 业务规则

| 编号 | 规则描述 |
|------|----------|
| BR-001 | 卖单仅支持单品固定价（FixedPriceForItem），NFT 数量必须为 1 |
| BR-002 | 买单支持集合出价和单品出价，可批量购买（amount > 1） |
| BR-003 | 撮合时卖单必须以 FixedPriceForItem 类型存在 |
| BR-004 | 成交价：卖方发起时取买方出价；买方发起时取卖方挂单价 |
| BR-005 | 同一 maker 不能同时作为买卖双方撮合 |
| BR-006 | 订单取消后 filledAmount 设为 uint256.max（CANCELLED），不可再参与撮合 |
| BR-007 | 订单簿按 collection + side 维度维护价格红黑树，同价位订单以 FIFO 队列排列 |
| BR-008 | Bid 方向最优价为最高价（红黑树 last），List 方向最优价为最低价（红黑树 first） |
| BR-009 | 查询时自动过滤已过期的订单（expiry != 0 且 expiry < block.timestamp） |
| BR-010 | 协议费 = fillPrice × protocolShare / 10000，从成交价中扣除 |

## 7. 非功能需求

### 7.1 安全性

| 编号 | 要求 |
|------|------|
| NFR-001 | 所有外部状态变更函数需加 `nonReentrant` 防重入 |
| NFR-002 | 关键操作需加 `whenNotPaused` 暂停保护 |
| NFR-003 | ETH/NFT 转移使用 SafeTransfer 库，防止 transfer 失败导致状态不一致 |
| NFR-004 | Vault 资产操作限制为仅 OrderBook 可调用 |
| NFR-005 | 批量撮合使用 delegatecall 隔离，防止单笔失败导致整批回滚 |
| NFR-006 | 合约预留 storage gap（50 slots）以支持安全升级 |

### 7.2 可升级性

| 编号 | 要求 |
|------|------|
| NFR-007 | OrderBook 与 Vault 均采用 OpenZeppelin Upgradeable 模式 |
| NFR-008 | 使用 Initializable 替代 constructor 进行初始化 |
| NFR-009 | 继承链中各模块独立 init 函数，保证初始化顺序正确 |

### 7.3 性能

| 编号 | 要求 |
|------|------|
| NFR-010 | 价格索引采用红黑树，插入/删除/查询均为 O(log n) |
| NFR-011 | 支持批量创建、取消、修改、撮合，减少用户交易次数 |

### 7.4 兼容性

| 编号 | 要求 |
|------|------|
| NFR-012 | 支持标准 ERC721 NFT |
| NFR-013 | 结算货币为原生 ETH |
| NFR-014 | Solidity 版本 ^0.8.19 |

## 9. 约束与假设

### 9.1 约束

- 仅支持 ERC721 标准 NFT，不支持 ERC1155
- 仅支持 ETH 作为支付代币，不支持 ERC20 代币结算
- 卖单不支持集合级别挂单（仅 FixedPriceForItem）
- OrderValidator 中定义了 EIP-712 相关常量，但当前版本撮合主要依赖链上订单验证

### 9.2 假设

- 用户在使用 Vault 存 NFT 前已对 Vault 合约执行 `setApprovalForAll`
- 链下订单场景下，NFT 仍保留在 maker 钱包中，撮合时直接转移
- 部署顺序：先部署 Vault → 部署 OrderBook → 配置 Vault.orderBook 与 OrderBook.vault
